# Stream Library server adapter

This packet implements the server-only Library VOD adapter and its unit tests. It does not wire a route, Server Action, or Library UI caller. The feature flag `STREAM_VOD_LIBRARY_UPLOAD_ENABLED` must equal `true`; it defaults off. The adapter uses only the fixed `vod_primary` registry slot and the server environment values `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_STREAM_TOKEN`. It does not use the existing customer-code setting or any browser-supplied provider account ID.

## Server entry points

`src/lib/stream-vod-library-server.ts` exports:

- `prepareStreamVodLibraryUpload`: verifies an authenticated coach/admin, checks the current fixed-account proof, and invokes the authenticated prepare RPC. It accepts only a stable request UUID, title, description, and a 64-character file digest. The prospective video UUID is derived on the server from the request UUID, so retrying the same request preserves the source identity.
- `startStreamVodLibraryUpload`: checks the authenticated work projection and issues one provider `POST` only after a fresh `claim_stream_media_create` response whose outcome and `create_authorized` flag both authorize this operation. An existing claim or non-reserved state can only recover a previously stored TUS capability through the authenticated capability RPC; it cannot repeat the provider `POST`.
- `getStreamVodLibraryUploadStatus`: read-only authenticated status. It remains available when the upload feature flag is off and returns only operation state and revision.
- `getStreamVodLibraryUploadCapability`: retrieves a bearer upload URL only through `get_stream_media_upload_tus_location` after current ownership, role, proof, fence, and transport checks. The service-only projection never contains the URL.
- `verifyAndCommitStreamVodLibraryUpload`: performs bounded exact-UID read-only GETs, records provider observations through service RPCs, binds only a matching ready/signed/creator/metadata readback, and commits through the authenticated finalization RPC. A completed durable receipt is returned before any provider request or new mutation.

Active upload work is re-read and checked against the configured `vod_primary` account ID before claim, provider HTTP, transport, observation, bind, or commit work. A current proof for another account does not authorize the configured account. Completed receipts can be recovered before provider credentials are needed. All methods re-read the verified user and current `profiles.role` from the server session context. Only coach/admin roles can use the Library upload path. `service_role` is used only for the narrow 315/615 RPCs; this module does not read lifecycle tables with `.from(...)`. Errors returned to callers are stable generic codes, without raw provider bodies, token values, bearer URLs, or database error text.

## Provider boundary

The adapter uses the documented fixed Cloudflare API origin and account path. Before active work, it may verify access to the already-registered account using `GET /accounts/{account_id}/stream?limit=1`. It requires HTTP 200 and a valid successful Cloudflare envelope, then records proof with `record_stream_account_path_verification`. It never registers or attests an account. A slot mismatch, malformed response, non-200 response, or failed verification write stops the operation.

The create request is one `POST` to the account Stream endpoint with `direct_user=true`, TUS 1.0.0, the validated upload length, the verified session UUID in `Upload-Creator`, and metadata assembled from the 315 immutable operation projection. Library duration stays at 7,200 seconds; the adapter accepts the existing maximum file size of 30 GiB and applies the existing six-hour upload expiry policy. Request identity, marker, source, actor, title, signed-URL requirement, duration, and expiry are fixed by server code and the durable projection, not supplied as provider authority by the browser.

The only UID source is the documented `stream-media-id` response header. The adapter never extracts a UID from `Location` or a response body. It validates a returned `Location` as HTTPS on one of the exact Cloudflare upload hosts and validates the API host path against the configured account before asking `record_stream_media_upload_transport` to persist it. The URL is stored only in the private transport row and can be returned only by the authenticated capability getter. Redirects are errors; create POST is never retried automatically. A lost or ambiguous create response moves toward recovery/unknown state and cannot authorize another POST. A valid UID with a missing or invalid Location is durably held without issuing a capability.

For readback, the adapter GETs the exact persisted UID under the configured account and validates the Cloudflare success envelope, any reported UID, creator, signed-URL flag, canonical marker/source/actor metadata, and readiness. It does not require the 615 `latest_exact_uid_get` item to contain a `kind` field: that RPC result is already filtered to exact UID GET observations and omits `kind`. If a transport URL was not durably recorded, its absent local expiry is unknown; it does not create a fabricated marker mismatch, and no upload capability is issued from that path.

The official Get Video API describes `maxDurationSeconds`, `uploadExpiry`, `requireSignedURLs`, `readyToStream`, and `meta` as optional; it documents `maxDurationSeconds: -1` as unknown and `meta` as user-modifiable. Therefore the adapter keeps title, duration, signing, and expiry restrictions in trusted create parameters, while treating absent optional readback fields as unknown. It verifies canonical marker/source/actor metadata and creator/signing/readiness when those fields are reported; explicit canonical mismatches or comparable explicit duration/expiry conflicts stay held. It does not rely on `meta.expiry` as proof. This follows the documented schema and does not claim that every live response omits optional fields. See [Cloudflare Get Video](https://developers.cloudflare.com/api/resources/stream/methods/get/).

A successful HTTP 200 without all required identity facts is not written to the observation ledger: the 615 projection classifies a recorded 200 with nullable identity flags as a permanent conflict. The adapter instead retries the same exact UID GET within its bounded retry budget. Once a required identity fact is explicitly contradictory, it records the false observation and stays held; a missing readiness field remains retryable only after the identity facts are complete.

Provider request timeouts cover both headers and response-body consumption. Account verification and exact-UID GET bodies are size limited and bounded by the same timeout. A body stall is treated as transient unknown: it records no partial observation and cannot bind or commit. Valid but not-ready responses and transient HTTP statuses receive at most three read-only attempts with short delays. Non-transient identity contradictions become a permanent hold through the 315 observation projection. No failed or unready readback can bind or commit.

The adapter accepts the canonical PostgreSQL UUID string shape without enforcing RFC version or variant bits. This is required because the 315 request-derived operation IDs can contain non-RFC bits. Client request IDs are still validated as UUIDs; the server's deterministic prospective video and transition request IDs are canonical UUIDv8 values.

The original upload byte length is not stored in the 315 transport projection. The adapter validates the length on the first provider create request, but does not claim it can reconstruct or replay an identical create after a lost response. The durable create claim and unknown state prevent such a replay. This packet does not promise that a browser can resume a TUS session after losing its only returned bearer URL.

## Unit coverage

The two Vitest files exercise the parsers and state machine with injected RPCs and a fake provider. Coverage includes disabled-flag short-circuiting; role and configured-account mismatch on current work; expired-proof verification; non-RFC operation IDs; the actual 615 exact-GET DTO shape; one-winner concurrent claims; claim/POST/record/advance unknown outcomes; empty 201 responses; UID-versus-Location separation; canonical metadata and explicit duration conflicts; optional expiry fields and unknown duration; UID-only transport without false expiry mismatch; no second POST; status and capability separation; bounded account-verification and exact-UID body stalls; transient/not-ready GETs; creator/marker conflicts; exact bind/commit; and recovery from a lost commit reply.

No production provider request, database call, Auth API call, route launch, or browser upload was run. The adapter has not been connected to callers. Caller wiring, browser TUS behavior, real Cloudflare responses, and end-to-end upload validation remain for the next reviewed packet.

- [Resumable and large files (TUS)](https://developers.cloudflare.com/stream/uploading-videos/resumable-uploads/): TUS metadata, creator, and the `stream-media-id` response header; the docs explicitly say not to parse the UID from `Location`.
- [Direct creator uploads](https://developers.cloudflare.com/stream/uploading-videos/direct-creator-uploads/): `Upload-Length`, TUS endpoint creation, and `Location` as the one-time upload URL.
- [Initiate video uploads using TUS](https://developers.cloudflare.com/api/resources/stream/methods/create/): documented API endpoint, TUS version, upload-length and metadata headers, accepted permissions, and 201 response.
- [Get video details](https://developers.cloudflare.com/api/resources/stream/methods/get/): optional readback fields, `-1` unknown duration, and user-modifiable metadata.
- [List videos](https://developers.cloudflare.com/api/resources/stream/methods/list/): fixed-account read endpoint used only for explicit access verification.
