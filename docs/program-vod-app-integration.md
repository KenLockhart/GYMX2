# Protected VOD application contract

This migration adds the database side of authenticated Cloudflare Stream VOD uploads and playback. Its standalone prerequisite is the accepted main baseline plus Program 1550/1560, Daily 190100/190200, and source migrations 300 and 310. It consumes the registry, intent, observation, source-binding, retention, cleanup, and Auth-proof records established by those migrations. All upload capability and abort evidence tables have row-level security enabled and direct table privileges revoked, including for `service_role`; callers use the narrow RPCs below.

The contract does not make provider HTTP requests, validate provider hosts, mint playback URLs, or change WHIP/WHEP/RealtimeKit paths. The future server adapter owns fixed-host validation and provider transport. The Program UI owns Program pages and actions; this packet only defines SQL interfaces.

## Upload and commit

1. An authenticated coach calls `prepare_stream_library_video_upload(request_id, prospective_video_id, title, description, file_digest)`. The database derives the owner, provider account, operation and intent IDs, request marker, metadata, fixed transport parameters, and profile fence. Retrying the same request returns the original operation only when the full request digest matches.
2. A signed-in member or coach calls `prepare_stream_community_video_submission(...)` at submit time. It checks posting rights and creates a private `only_me` **general** post plus immutable processing intent. The intended kind, body, audience, optional coach, actor, and file digest are bound into the intent. Publication receipts authorize the one atomic change from the private general parent to those intended fields after current policy is checked again.
3. The trusted adapter calls `claim_stream_media_create`. Only `create_authorized` from the first successful compare-and-swap authorizes a provider POST. An exact replay returns `recovery_required` with `create_authorized: false`; it is not a second POST authorization. Changed operation/request digests fail closed.
4. `record_stream_media_upload_transport` records the service-observed UID, optional TUS Location, expiry, fixed original parameters, metadata, and provider evidence. A missing Location is represented as a typed recovery hold. The SQL layer does not infer a URL from a UID or accept caller-selected provider host/parameters.
5. `get_stream_media_upload_status` returns only the operation state and revision. `get_stream_media_upload_tus_location` is separate and returns the bearer Location only to the initiating, currently eligible signed-in actor while the exact operation and parent fence remain active, the account is verified, and the capability has not expired. It serializes on the account and parent locks, then rechecks the current role, tombstone, operation, and fence before returning the bearer value. It returns unavailable after cancellation, source commit, role loss, or account tombstoning.
6. The adapter records trusted provider observations through the 310 observation RPC. `bind_stream_media_upload_readback` remains the sole canonical provisional-binding operation and requires exact ready GET evidence. For Library uploads, `commit_stream_library_video_upload` inserts the prospective `videos` row, advances the binding and asset, completes the operation, and opens the serialized owner profile fence in one transaction. No caller UID or owner override is accepted.
7. Community publication uses `publish_stream_community_video_submission`. It rechecks current account eligibility, intended posting rights, membership where required, the unchanged and unremoved private parent, and the exact completed media binding. It inserts `post_media`, applies the intended audience, completes lifecycle evidence, stores the replay receipt, and marks the processing record published in one transaction. Direct promotion or edits while processing are blocked. A video-only post may keep an empty body.

Upload preparation returns an operation ID and the immutable request/transport fields needed by the adapter. Status and playback responses contain no TUS bearer capability. Direct Program lesson, intro, Daily Content, and Daily Fuel uploads remain unsupported: use a verified Library video and the existing guarded source attachment paths.

An initial Program intro reference is validated by the Program intro policy and the media reference guard. Because the media guard is a `BEFORE INSERT` trigger and the Program row is not yet visible, the 315 migration additively replaces the generic 310 guard and derives only an initial intro’s source owner from `NEW.coach_id`. It preserves the 310 UPDATE/DELETE, identity, fence, UID, and cleanup checks. The guard also rereads the exact paid lesson owner and current Library video identity, readiness, and protected visibility after it acquires the media locks.

Library upload preparation preserves the existing server route limit of 7,200 seconds; community video submissions retain their 600-second limit. The value is server-derived, included in the immutable operation/transport identity, and returned with the original transport DTO. It is not selected by the browser.

## Cancellation and account cleanup

The actor requests cancellation with `request_stream_media_upload_cancel(operation_id, stable_request_id)`. The API accepts only the initiating owner and supported app-upload sources.

- A ready-but-uninserted `provisional_bound` upload uses its real canonical 310 binding in a cleanup manifest. The binding must be ready, signed, creator-matched, and marker-matched. It is detached only after terminal provider absence is recorded.
- A `create_unknown` or `created_unverified` upload can enter the separate immutable cleanup-only abort manifest only after the trusted service response has durably recorded the exact UID and an exact UID GET confirms the upload creator and intent marker. This lane has no canonical asset, source binding, or publication-complete claim. Unknown UID, conflicting identity, active reference, retention, legacy ambiguity, or competing cleanup stays held.
- A 2xx DELETE response is not sufficient by itself: finalization also requires an exact GET 404 for the same registry and UID. If the DELETE response was lost, a durable `delete_started` event followed by a trusted exact GET 404 can record `already_absent_confirmed`. A 403, timeout, malformed result, present object, or bare DELETE 404 is not absence proof.
- The cleanup worker receives a UID only from `get_stream_media_upload_cancel_work`, after the manifest, source fence, account, reference, and retention checks pass. It uses the 310 `start_stream_media_uid_delete` and `record_stream_media_uid_delete_result` APIs. The actor-facing response does not return a provider URL or UID.
- Cancellation is terminal only after an immutable receipt joins the original intent/context, provider observation, exact UID, cleanup manifest, DELETE-start/result history, exact absence, and advanced parent fence. Late exact UID-present observations invalidate the proof. A private database sequence records commit-independent insertion order for trusted UID observations and delete events. Receipt checks compare those sequence values, so transaction timestamps cannot reorder evidence when one transaction starts earlier and records later.
- Account deletion calls the service-only `begin_stream_account_media_cleanup`. When 310 reports an unresolved known-unready upload, 315 derives its identity from the account tombstone and persisted intent, creates a separate binderless abort manifest, and returns pending work. The service worker obtains the exact UID through `get_stream_media_upload_cancel_work`, records DELETE and exact GET evidence through the 310 RPCs, then finalizes the upload cancellation before the account cleanup inventory can finish. This lane does not create a canonical asset or source binding. Unknown UID, lost or ambiguous create identity, timeout, 403, a present object, or a bare 404 remain holds.

The 315 component `vod_upload_abort` extends the 310 Auth cleanup resource set. Its digest is derived from each account’s upload/receipt inventory and is recomputed when proving readiness and when `private.stream_auth_contract_current` consumes an Auth permit. 315 replaces `prepare_stream_auth_deletion_permit` with the same signature and its original 310 checks, plus a VOD-proof freshness check before creating or revalidating permit snapshots. This prevents an old ready proof from being copied onto a permit after a late observation changed the upload inventory. The 315 `private.stream_auth_contract_current` body remains stable for later component composition. `begin_stream_account_media_cleanup` routes through the 310 implementation only after every canceled upload has a valid terminal receipt; 310’s unresolved `created_unverified` path remains a hold.

## Playback projections

Authenticated RPCs return only `{ outcome, registry_id, provider_uid, source_kind, source_identity }` (and the relevant video/media ID). They return no provider URL, signing token, upload capability, or generic “actor may read UID” result. Each lookup checks the exact current caller context and its exact 310 binding/asset evidence before returning a UID for a future server signer. 315 adds attachment events after the 310 guarded write for exact ready Program intro, Program lesson, Daily slot, Daily Fuel assignment, and member bookmark bindings; it never turns missing or unready source data into a ready asset. A Library video remains available during the exact same-owner profile fence for a different active Library upload, provided the video's own binding and asset remain ready and its UID is not reserved. Cleanup fences, account tombstones, and every other active-source fence still block access. Program and Daily contexts require their exact parent fence to be open and free of cleanup. Parent revision counters may advance for unrelated uploads or newer Program versions without replacing an immutable lesson identity. Program lessons use the immutable lesson UID and `program_lesson` binding; they do not substitute a later UID from a Library video row. Program intros and current Daily contexts resolve their current referenced video through their own context binding. A future thumbnail signer must use the same context-scoped projection and accept source context IDs; it must not expose a generic UID or thumbnail lookup.

| RPC | Context checked |
| --- | --- |
| `get_my_stream_library_video_playback(video_id)` | The caller owns the ready Library video and exact binding. |
| `get_visible_stream_post_video_playback(post_id, media_id)` | The post is currently visible and unremoved; the media ID belongs to that exact post and has one unambiguous ready binding. Community `post_media` can play without a parallel `videos` row. |
| `get_stream_program_intro_playback(program_id)` | A signed-in regular member can currently access the published Program. This allows an eligible unpaid preview. |
| `get_my_stream_program_order_lesson_playback(order_id, lesson_id)` | The caller’s immutable order and current installment/timeline stage expose the lesson, and its UID is exclusive to paid content. |
| `get_my_stream_program_enrollment_lesson_playback(enrollment_id, lesson_id)` | The caller’s free enrollment snapshot, current Program eligibility, and daily stage expose the lesson. |
| `get_my_stream_daily_content_video_playback(slot_id, revision_id)` | The current resolved daily gate selects that exact published slot and revision. |
| `get_my_stream_daily_fuel_assignment_playback(assignment_id)` | The caller is the member named by the current-day assignment. |
| `get_my_stream_daily_fuel_bookmark_playback(video_id)` | The caller owns the bookmark and the exact member-owned bookmark binding; the coach-owned video row is validated separately. |

Paid lesson playback rejects a lesson unless its snapshot is paid and `program_only`, its order access helper exposes the exact lesson, and the same registry/UID is not also used by a Program intro, free snapshot, member-visible Library video, or shared community post. Existing visibility and retention guards in 1550, 1560, and 310 remain authoritative.

The `videos.visibility` constraint accepts only `private`, `members`, and `program_only`. Visibility updates run at `READ COMMITTED` and try the owner account, video parent, and UID locks in that order before checking current paid-retention references. Lock contention returns `55P03`; callers retry the full transaction after the competing write commits. A retained paid UID cannot be changed to `members`; once it is `program_only`, it also cannot be changed back to `private`. The guard applies to authenticated and service-role updates and does not accept an operation-GUC match as an override. An ordinary nonpaid Library video can still move between `private` and `members`. Paid lesson attachment uses the corresponding owner, source-parent, and UID try-locks, then rereads the exact Program owner and current Library row; it accepts only the exact ready, signed, protected video identity. A successful retry evaluates committed row and retention state. Paid order playback uses `private.current_daily_checkin_day()` so installment access and strictly increasing lesson timeline days use the same production Eastern calendar helper.

## Test scope

`supabase/tests/stream_media_app_contracts_test.sql` is a rollback-only pgTAP suite. It uses synthetic auth identities and provider-like values only through the trusted provenance/lifecycle RPCs. It covers the existing two-hour Library transport policy, replay under later ready and contradictory observations, two sequential Library commits plus pre-create cancellation, playback of the first Library video while the second upload owns the profile fence, atomic Library commit, private community processing/publication, exact visible post-media projection, actor cancellation continued by account cleanup after session loss, immutable cancel replay, same-transaction evidence ordering, lost-DELETE reconciliation, late contradictory observations, a shared-UID hold, and canonical provisional cancellation. It also checks ordinary `private`/`members` changes, rejects arbitrary visibility values, proves an authenticated coach cannot downgrade a retained private paid UID, compares the video, source bindings, attachment history, and parent fences before and after that rejection, checks the Task and Daily Fuel RPC denials, and verifies service-role cannot downgrade `program_only` media. It checks a signed-in nonbuyer cannot directly select that protected row. Intro tests cover a valid initial Program intro insert and reject foreign private media, a forged Program owner, and program-only intro media, confirming failed inserts leave no Program binding or attachment event. The suite checks attached evidence emitted from normal Program and Daily guarded writes, both paid lessons in one immutable version, a same-day block after the second installment, access on the next Eastern timeline day, and grandfathered paid/free lessons after each Program publishes a newer content version. The Daily test records the actual Eastern base date and original clock helper definition before its transaction-local test clock override, then restores the production day before free-enrollment cases. On the standalone 310 baseline, the only registered Auth components are the existing `vod_media` component and 315's `vod_upload_abort` component. The suite asserts a service-side `permit_ready`, checks `private.stream_auth_contract_current`, records an unknown Auth result using the revision returned by the start RPC, then checks same-permit revalidation and the next Auth call after a late UID-present observation invalidates the VOD inventory proof. It does not invent unrelated feature component proofs. A later companion suite must test the combined component set after its owning migrations are present. The two-connection tombstone, latest-observation, chronology, and paid visibility/attachment cases are acceptance procedures in `.vercel/stream-media-app-contracts-qa/race-cases.md`; these race cases remain unexecuted.
