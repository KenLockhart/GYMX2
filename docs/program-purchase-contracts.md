# Program purchase app contracts

This packet adds the buyer quote, owner recovery, safe order context, and atomic consent boundary for Programs. It does not start checkout or call a payment provider. Existing free enrollment, provider checkout, webhook, invoice collection, cancellation, and refund paths remain separate.

## Buyer facing operations

`public.get_my_program_purchase_quote(uuid, smallint, text)` is executable by `authenticated`. The actor comes from `auth.uid()`. The input contains only Program, installment count, and optional promotion code. The function returns the current published paid offer, immutable lesson count, normalized promotion code, server calculated list/discount/total amounts, canonical installment split, maximum installment count, quote digest, and exact future dates for installment purchases. It reads promotion quota without reserving it. The reservation RPC rechecks eligibility and quota under its existing locks.

`public.get_my_program_purchase_request(uuid)` and `public.get_my_program_purchase_context(uuid)` are owner scoped and executable by `authenticated`. Recovery searches only the caller's UUID request key. Context returns the order's immutable buyer, Program, offer, price, promotion, plan, order/billing state, current billing revision, accepted terms, and settlement/cancellation summaries. Before consent is saved, a paid order may correctly have `terms: null` and `billing_revision: 0`; after consent is saved, terms must be present with a positive revision. A zero-total grant retains `terms: null` and revision zero. Context does not return customer IDs, payment intent IDs, checkout URLs, or other provider credentials. Both reads remain available after the caller's current membership or offer eligibility changes so a saved consent can be recovered.

The TypeScript adapter in `src/lib/program-purchase-server.ts` checks `PROGRAM_PURCHASE_ENABLED === "true"` before authentication or an RPC for quotes and new confirmation. That flag defaults off. Owner recovery reads are independent of the flag. It derives the buyer from the authenticated Supabase client, rejects extra or malformed DTO fields, and creates the service client only after a fresh quote matches the pinned offer and the buyer has provided the required consent.

## Atomic confirmation

`public.confirm_program_purchase(uuid, uuid, uuid, smallint, uuid, text, text, date[], boolean, boolean)` is executable only by `service_role`. Its arguments are the authenticated buyer ID supplied by the server adapter, Program ID, pinned offer ID, installment count, stable request UUID, normalized promotion code, expected quote digest, quoted charge dates, billing consent, and off-session consent. No client supplied amount, seller, connected account, or provider ID is accepted.

The function first locks the buyer request scope and looks for an existing order with that buyer/request UUID. An exact retry is compared against the stored Program, offer, installment count, and promotion, then returns the original grant or saved billing revision. This path does not recheck current membership, offer, promotion quota, or a quote date that may have changed after the original confirmation. Reusing the UUID with a different bound purchase payload returns `request_conflict`.

For a new request, the function calls the existing `create_program_order_reservation` and `prepare_program_billing_terms` functions in one outer database transaction and one exception-protected subtransaction. The existing reservation function owns the buyer, Program, and promotion locks and derives the immutable amounts. After reservation, the wrapper rechecks account ingress/deletion/tombstone fences and the buyer's current member, tier, coach link, and published Program eligibility. It performs this check for zero-total grants too, since those do not call the billing-terms function. After the locks are held, the wrapper recomputes the quote digest and dates from the created order. A changed quote rolls back the order and any promotion reservation. A terms write that does not return its first saved revision also rolls the order and promotion reservation back. Unexpected database errors propagate and roll back the whole RPC.

Every positive paid quote requires each charge to be at least 50 cents, including pay-in-full. Paid orders require explicit billing consent. Installments additionally require off-session consent and the fixed seven day retry window. A 100 percent promotion follows the existing zero-total grant behavior with installment count zero; it creates no billing terms or provider rows. A lost zero-total grant response is recovered with the same request UUID without requoting or creating another grant. The wrapper does not create a saved-card or provider customer record.

## Installment calendar

The quote uses the current date in `America/New_York`. The first future charge is one calendar month later, clamped to that month's final day. Later charges follow the first future date's day, or remain at month end when the first date was clamped to month end. For example, January 30, 2027 produces February 28 and March 31. January 29, 2028 produces February 29 and March 31. The digest includes the schedule policy version and the exact dates. Confirmation recalculates both after the existing reservation locks are acquired; it rejects a stale schedule instead of silently changing the terms.

Saved terms are immutable. A retry returns the original terms and current billing revision. It does not submit revision zero again or overwrite the accepted dates.

## Access and validation

The migration revokes direct order, promotion, and billing table access from the app roles. The three buyer reads use caller identity and the confirmation write uses the trusted server role. Private digest/calendar helpers have no app-role execute grant. TypeScript DTO parsers require exact key sets, bounded integer cents, canonical installment splits, valid UUIDs/dates/digests, and matching billing revision semantics for paid versus free outcomes.

The TAP file builds local synthetic auth, Program, entitlement, and promotion fixtures. It covers quote math and the 1/49/50-cent boundary, membership/link rejection, owner isolation, pre-consent context, consent, stale promotion quota, free grants and exact grant replay, a test-local post-reservation account fence, request replay after current offer/membership changes, and rollback after a synthetic terms-write failure. On 2026-11-21, the frozen 620 migration was applied once atomically to the fresh local clone `gymx2_program_purchase_app_20261121b1` from `gymx2_program_media_origin_20261121p5`; the source remained unchanged. PostgreSQL created all nine functions with `check_function_bodies=on`. `plpgsql_check` 2.8 reported zero errors and two warning groups for unused/shadowed `v_index` loop variables. The standalone TAP run passed all 79 assertions in order, with no failed assertions or SQL errors, the final `1..79` plan, and an explicit final `ROLLBACK`. Post-run checks found no fixture UUID references and matching existing function, trigger, privilege, component, and helper fingerprints in source and clone. The focused TypeScript tests passed 20/20 across two files; scoped ESLint and full TypeScript checking exited 0. The promotion interleaving is sequential and does not test concurrent transactions; no time-based lock wait was simulated.

Checkout creation/retry, provider calls, webhook reconciliation, later invoice collection, cancellation, refund behavior, user interface, deployment flags, and end-to-end provider validation remain separate work.
